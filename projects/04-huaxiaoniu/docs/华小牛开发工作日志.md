# 华小牛开发工作日志

记录日期：2026年10月13日

这次课程项目的要求是参考 pi Agent 的架构，结合自己的专业或兴趣搭建一个 Harness。我选的是 AI 桌宠，名字最后定为“华小牛”。希望它除了能在桌面上显示和聊天，还能帮我读一个本地项目，说清楚里面有哪些文件、主要做什么。

项目是在 Codex 辅助下开发的。我先把功能要求、技术路线和验收要求整理出来，再让 Codex 按步骤编写、运行和检查代码。下面按实际开发顺序记录，没有把同一天的工作拆成几天。

## 一、先把要做的东西定下来

我比较熟悉 Python，所以界面选择了 PySide6。Agent 部分使用 pi，通过 RPC 和 Python 通信。这样，模型请求和工具调用循环可以复用 pi，桌宠窗口、任务管理、文件访问限制这些内容由项目自己实现。

第一版的任务也没有定得太多，先做“读取这个项目，介绍它的结构和主要功能”。这个任务比较适合检查程序是不是真的能用：要先选目录，再调用工具读取文件，最后才能给出有依据的介绍。

外观暂时用程序画一只小牛。项目一开始的名字叫“小猫”，后来改成了“华小牛”。先把功能做通，再考虑换更完整的角色素材。

## 二、检查环境和安装依赖

开发前先检查了当前目录，以及电脑上的 Python、Node.js 和 pi。电脑上有多个 Python 版本，也有 Node.js，但没有找到可直接使用的 pi 安装。项目最终使用 Python 3.14，并在单独的 `huaxiaoniu` 文件夹中创建虚拟环境。

安装过程遇到了几个环境问题。npm 的全局缓存报了 `EEXIST` 错误，后来改用项目自己的缓存目录；uv 创建环境时遇到跨磁盘临时文件问题，就改用 Python 自带的 `venv`。这些问题没有通过修改系统权限来处理，尽量把调整留在项目目录内。

安装后的主要版本是 PySide6 6.10.2 和 pi 1.2.0。pi 使用项目内安装，并保存了依赖锁文件，方便换一台电脑时装出相同的版本。

在接 RPC 之前，还查了 pi 官方文档，并对照安装版本的帮助信息核对命令和事件格式。这里不能直接照搬旧教程，因为事件名称和工具配置方式会影响后面的判断。

## 三、先把桌宠窗口做出来

界面分成两个窗口：一个是桌面上的小牛，另一个是双击后打开的聊天工作台。

桌宠用 PySide6 的 QPainter 绘制，先做了透明背景、拖动、置顶和右键菜单。聊天窗口关闭后，桌宠仍然保留；需要完全退出时，从桌宠右键菜单退出。

这一步主要检查窗口能不能正常显示和操作，没有把时间放在美术上。角色暂时比较简单，但能看出是一只小牛，也可以根据不同任务状态改变表现。

## 四、接通 Python 和 pi

桌宠窗口能运行后，开始连接 pi。Python 使用 Qt 的 QProcess 启动后台进程，向 pi 发送 JSON 消息，再接收它返回的事件。

这里采用异步处理。模型回复可能需要等一段时间，如果主界面一直阻塞着等待，桌宠就会拖不动，停止按钮也点不了。QProcess 的输出通过信号送回界面，等待模型时，窗口仍然可以继续响应。

通信解析单独放在 `agent/protocol.py`。后台一次输出的数据不一定刚好是一条完整消息，中文字符也可能被拆开，所以需要先按字节缓存，再按换行分出完整的 JSON。测试中检查了中文分片、不同换行格式和错误数据，避免只在最简单的情况下能通信。

还有一个需要分清的地方：pi 接受了消息，不代表任务已经完成。程序要继续接收事件，等到整次运行结束，再判断是成功、失败还是被停止。

## 五、给文件读取加上限制

这个项目要读取本地文件，不能只考虑能不能读，也要考虑允许读到哪里。

查文档时确认，pi 的工作目录并不等于安全隔离。即使把目录设置为某个项目，也不能据此认定它只能访问这个项目。因此，第一版没有直接开放默认的读写和命令工具，而是只提供两个自定义工具：列出项目文件、读取项目文本。

具体的检查放在 `agent/file_tools.py`。工具只接受项目内的相对路径，拒绝用 `..` 跳到上级目录，也限制了文件大小，并过滤隐藏文件、常见凭据文件和链接。单个文本文件最多读取 64 KiB，目录列表最多返回 200 项。

pi 和 Python 文件工具之间有一个很薄的 TypeScript 扩展。它负责注册工具，再调用固定的 Python 脚本，不允许模型传入任意命令。

这些检查能限制第一版提供的读取能力，但还不能把整个程序当作系统沙箱。普通文件里也可能有过滤规则识别不出的敏感内容，所以演示时仍然应该选择适合提供给模型的项目。

## 六、把聊天、工具记录和宠物状态连起来

接下来把聊天窗口和后台事件连起来。聊天区逐步显示回复，右侧记录工具活动，比如开始列目录、读取了哪个文件，以及读取的字节数。

宠物设置了待机、思考、工作、完成、失败五种状态。状态根据实际事件变化。例如，收到工具开始执行的事件后，才显示正在工作。对于“介绍这个项目”这个任务，如果本轮没有成功读取文件，就不能因为模型说了一句“完成了”而显示成功。

同时加入了停止和超时处理。点击停止后，先请求 pi 取消任务；如果两秒内没有结束，再强制结束 pi。单次任务设置了 120 秒超时，并限制最多 12 轮模型请求、24 次工具尝试，防止任务一直重复下去。

测试时还发现，停止之后可能继续收到迟到的错误消息。如果直接处理它，就会把原来的“已停止”或“超过轮数限制”覆盖掉。后来调整了事件处理顺序，让已经确定的停止原因保留下来。

## 七、保存设置和恢复会话

宠物名字、用户称呼、选择的项目目录和置顶状态，用 JSON 保存。聊天历史则优先复用 pi 自己的会话文件，程序只记录项目与会话的对应关系。

这部分发现过一个比较实际的问题：切换项目时，旧 pi 进程还没有完全退出，旧会话就可能被记到新项目下面。后来把“用户当前选择的项目”和“正在退出的进程所属项目”分开记录，并加了测试，确认换项目后不会恢复另一份项目的聊天内容。

代码检查还发现，模型切换也需要等待确认。原来的处理会先保存新模型，但 pi 可能还没有切换成功，这时发消息就可能用到旧模型。修改后，切换期间先禁用发送，收到成功响应再保存。如果保存的模型已经失效，也可以从界面恢复默认模型并重连。

## 八、运行测试和尝试真实模型

开发阶段的完整测试结果是 44 项通过，1 项跳过。跳过的是文件符号链接测试，因为这台 Windows 电脑没有相应的创建权限；硬链接和 Windows junction 的检查另外做了测试，并且通过了。

除了单独测试文件和状态逻辑，还搭了一个本地协议测试服务，让真实的 pi 进程调用真实的 Python 文件工具。通过这种方式，检查了列目录、读取文件、展示结果、保存会话和重启恢复，也检查了模型等待时拖动桌宠、停止任务、超时和后台退出。

本地测试服务的回复是测试程序安排的，不是真实模型生成的。这些测试能说明程序各部分可以接起来，但不能代替真实模型验收。

随后尝试使用电脑上已有的 Anthropic 认证发起真实请求。pi 能识别到认证配置，但服务端拒绝了请求，因此没有得到真实模型回复，也没有完成真实模型阅读项目的成功演示。目前已经提供本机登录脚本，下一步需要重新登录后再验证。

## 九、整理名称和说明文件

最后把名字统一改成了“华小牛”，更新了界面文字、默认宠物档案和模型提示词中的称呼。已有的数据目录保留原来的标识，避免改名后找不到之前的设置和会话。

README 中整理了安装、启动、模型配置、项目目录、架构和演示步骤，也单独记录了哪些功能已经测试、哪些还没有验证。源码包没有放入本机凭据和运行会话。

目前桌宠能够独立启动，窗口操作、后台通信、受控文件工具、任务管理和会话恢复已经做出来。接下来先处理 Anthropic 登录，用一个实际项目跑完“选目录、读文件、生成介绍、重启恢复”的流程，并对照文件检查介绍是否准确。外观、Git 改动总结和装饰功能放在这之后再做。
