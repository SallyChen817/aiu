任务一工作日志

整理日期：2026-10-11

最初的想法

我想做一个本地学习和待办助手，既能回答学习问题，也能记录任务、根据进度给出建议。整体按照本地模型、Dify 智能体、自己的网页这三个阶段推进。遇到不懂的配置和报错，我先向 AI 询问原因，再按建议操作、反馈结果，逐步把流程连起来。

2026-10-08：本地模型和 Python 调用

结合电脑配置，我选择用 Ollama 运行 qwen3.5:4b，并通过 test_Ollama.py 请求本地接口，让模型生成 Python 学习计划。

这一阶段主要卡在版本、代理和输出编码上。根据 AI 给出的排查建议，我检查 Ollama 版本，让本地请求绕过代理，并将输出设为 UTF-8。调整后，本地聊天和 Python 调用都能正常得到回答。

2026-10-08 至 2026-10-09：部署 Dify

我按照 AI 提供的步骤安装 WSL、Ubuntu 和 Docker Desktop，再部署 Dify 1.17.1，通过 Ollama 插件接入本地模型，创建“学习任务助手”。

环境准备花的时间较多，主要遇到 Ubuntu 下载失败、源码下载超时、Docker 的 WSL 集成未启用，以及容器连接本机模型失败。我根据报错逐项调整下载方式、集成设置和连接地址，最后跑通了基础聊天。

这时我发现，只有问答还不能结合自己的实际进度，所以决定继续接入任务数据库和查询工具。

2026-10-09 至 2026-10-10：处理数据和启动问题

重启后，Dify 多次要求重新创建管理员，工作室也变成空白。排查后发现，原数据还在，但容器读到了另一份空数据库。

我在 AI 协助下先备份数据，再调整保存方式。最初只找回账号和“测试”应用；后续改用 Docker 持久数据卷，恢复了“测试”和“学习任务助手”，并完成停止、重新启动服务后的数据保留检查。

之后还遇到网页打不开的问题，这次是部分容器没有启动，不能直接当作数据又丢了。这个过程让我确定了排查顺序：先看服务是否运行，再检查账号、应用和数据。整台电脑重启后的完整验收仍需补做。

2026-10-10：接入任务查询和网页

我把项目进度放进本地 SQLite，按 AI 的指导在 Dify 中接入查询工具和 Agent 节点，测试“我已经完成什么，今天有两小时该做什么”。运行记录中能看到工具读取真实任务，再由模型根据结果给出建议。

过程中遇到工具有结果但页面没有正文的问题。我根据运行记录检查回复变量和节点连接，调整后能正常显示回答，普通学习问答也保留了。

随后，我在 AI 辅助下完成自己的网页，通过 Python 后端连接 Dify API，展示聊天、任务清单和工具调用结果，并整理了统一启动入口。这里的任务进度来自数据库记录，需要人为更新，不是自动检测电脑得到的。

2026-10-10：增加多清单和确认保存

最初只有固定的五项项目任务，我希望还能记录每天的待办，因此提出保留原清单、支持多份清单切换，并通过聊天批量添加事项。

我优先采用 Dify 已有的 SQLite 插件，按 AI 的说明配置查询、参数提取、条件分支和人工确认，再在辅助下完善批量新增、修改状态、删除和保存后复查。新任务默认未完成，增删改都先展示确认内容，取消就不保存。

主要问题是确认前提前回复、保存格式不正确，以及模型漏掉部分事项。我结合页面表现和执行记录逐项核对，最终把确认卡片和清单切换接入网页。发布后又发现编辑器显示旧流程，核对并恢复草稿后，草稿与发布版保持一致。

当日验收记录显示，14 项数据库及操作测试、9 项网页服务测试通过，实际流程覆盖新增、追加、修改、取消、删除、切换和刷新保留。测试使用独立数据库，原来的五条项目任务没有被测试改动。

2026-10-11：核对完成情况

我请 AI 结合已发布流程和运行记录检查项目，确认现在已经具备理解请求、查询数据、确认修改、执行保存和复查结果的完整流程，也已经接入自己的网页。

检查中发现，模型仍可能在同一条回答里对任务是否完成给出矛盾说法。下一步应优先让状态说明与数据库一致，再补整机重启和确认超时的完整测试。流程运行成功，不代表回答内容一定正确。

目前进度和后续安排

任务一的本地模型部署、智能体工具接入和 Web 应用已跑通。接下来重点完善稳定性、整理 Git 提交并推送 GitHub。知识库作为后续扩展，不影响当前清单管理流程。这份日志按已有聊天和验收记录整理，未验证的内容继续保留为待办。
